SPOTIFY

Почему микросервисы?

Изначально у Spotify была монолитная система. Но по мере роста пользовательской базы и усложнения функционала (добавление подкастов, аудиокниг, сложных рекомендаций) монолит стал узким местом:

Сложность обновлений. Чтобы выпустить даже небольшую фичу, приходилось пересобирать и развёртывать всю систему целиком, что вело к длительным простоям. 
Проблемы с масштабированием. Если одна подсистема (например, сервис рекомендаций) начинала испытывать нагрузку, приходилось масштабировать всё приложение целиком, даже если другие части простаивали. 

Высокие зависимости. Разные команды не могли работать параллельно — возникали «узкие места» в координации. 
Переход к микросервисам решил эти задачи. Система разбилась на независимые сервисы, каждый из которых отвечает за свою бизнес-задачу: управление пользователями, работа с музыкальным каталогом, стриминг аудио, поиск, формирование рекомендаций, биллинг и т.д.. Это дало несколько ключевых преимуществ:

Независимое масштабирование. Нагрузку можно наращивать точечно: если сервис рекомендаций стал узким местом, масштабируют только его, не трогая остальные части. 
Гибкость разработки. Разные команды могут параллельно развивать свои сервисы, не блокируя друг друга. 
Изоляция сбоев. Падение одного сервиса не обрушивает всю систему целиком. 
Упрощение обновлений. Новые версии можно развёртывать для отдельных сервисов без остановки всего приложения. 


Для асинхронного обмена данными между микросервисами Spotify использует Apache Kafka. Через Kafka система в реальном времени собирает и передаёт события: пользователь включил трек, поставил лайк, создал плейлист. На основе этих потоков строятся рекомендации, обновляются профили пользователей, работают другие динамические функции. Для синхронных запросов (например, при авторизации или поиске) сервисы общаются через REST API или gRPC
